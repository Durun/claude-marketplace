## 指摘（目線ごと、重い順）

### 性能・GPU・I/O

1. 書き出し用の Chrome は `--force_high_performance_gpu` で起動し、`WEBGL_debug_renderer_info` で NVIDIA を選んだか確かめ、違えば止める。プレビューの UI にも選ばれた GPU の名前を出す。
2. 書き出しは、ブラウザの中の VideoEncoder でエンコードし、mediabunny で MP4 に詰める。フレームを Chrome の外に出さない。Chrome を 3〜4 個並行に起動すれば、21 分 60 fps を 4〜8 分の見込み。
3. `text.html` を毎フレーム描かない。パラメータごとに 1 回描いてテクスチャにする。ふつうの字幕は Canvas2D か MSDF で GPU に描く。HTML-in-Canvas（`drawElementImage`）は origin trial なので試すだけにする。
4. 音: 11 時間を decodeAudioData で読むと 15 GB。取り込みでトラックごとに区切った PCM か Opus を作り、カットの範囲だけ読む。書き出しは OfflineAudioContext か自前のミキサー。
5. フレームのキャッシュは RAM や VRAM には入らない（1080p の RGBA で 1 分 30 GB）。描いた区間を短い GOP でエンコードして NVMe に置く。キーの「画面上の大きさ」は段階に丸める。
6. レンダラーを Worker と OffscreenCanvas に出して UI と分ける。ドラッグ中の操作は 1 つにまとめる。
7. 拡大するカットは、540p のプロキシではぼやける。止まっているときは原本に切り替えるか、そのカットだけ 1080p のプロキシを作る。中間の絵は RGBA16F。
8. 原本は T500、プロキシとキャッシュは T705 に分けると、読みと書きがぶつからない（60%）。撮影中の取り込みは、OBS の NVENC と取り合わないよう抑える。

### データの規模とランタイム

1. 書き出しの経路（上の 2 と同じ）。geneva に分ける案は、種類を足すたびに 2 重の実装になるので採らない。
2. `project.json` を 1 つにしない。索引と設定の `project.json`、`comps/<id>.json`、`assets/<id>.json`、`transcripts/<assetId>.json` に分け、変わったファイルだけ書く（FCP の `.fcpbundle`、Unity の `.meta`）。
3. 書き込みはアトミックに（一時ファイル → fsync → rename）。復旧は「最後のスナップショット + その後の ops.jsonl の再生」（Redis の RDB + AOF、SQLite の WAL）。
4. 操作に逆操作を持たせ、ドラッグの連続はトランザクションにまとめる。操作に「触る所」（`touches`）を宣言させ、同時書き込みの判定を機械的にする。CRDT（Automerge、Yjs）は要らない。
5. git には文書と review を入れ、ops.jsonl とキャッシュは外す。ops はスナップショットごとにローテーションする。検索の索引と ops の照会は SQLite（`node:sqlite`、FTS5）の再生成できる派生物にする。
6. 単語の ID は「素材 + 開始の時刻」の決定的な値にする。
7. プロキシはプロジェクトの外の決まった置き場所に置き、素材の中身のハッシュで引く（Premiere の Media Cache、Resolve の Cache Files）。
8. 書き出し中は、自動の改善によるサーバーの読み直しを待たせる。

### 映像エンジンの開発者

1. 色の管理の層がない。作業色空間は線形の Rec.709 で RGBA16F。素材ごとに入力の色空間を持つ（OCIO の型）。YUV→RGB はブラウザに任せず、Y と UV の面を受けて自前のシェーダーで変換する。プロキシも書き出しも bt709・tv のタグを明示する（FFmpeg の既定は BT.601）。8 bit に落とす前にディザー。アルファは中ではすべて premultiplied の線形。合成のガンマを選べるようにする（AE の「1.0 ガンマでブレンド」）。HDR の素材は断るかトーンマップを明示する。
2. 時刻を有理数か整数の tick にする（OTIO の `RationalTime`、FCPXML の `1001/30000s`）。素材のフレームを選ぶ規則を 1 つに決め、量子化は葉で 1 回だけ。VFR は取り込みで PTS の索引を作り、プロキシも PTS を保つ。OBS の mkv の音と映像の頭のずれを扱う。
3. ノードの口を OpenFX に寄せる: 非同期の描画、時刻で引ける入力（`getFramesNeeded`）、描く領域（RoD、RoI）、`isIdentity`、アルファ・ビット深度・画素の縦横比の宣言。
4. キャッシュのキーに、素材の中身のハッシュ、素材のフレームの番号、品質（プロキシか原本か）、作業色空間、レンダラーと種類の版を入れる。時刻で変わらない種類は t を外す。`deterministic` は「同じ機械、同じ実装の上で」と定義する。
5. 音は自前のミキサーで、Float32・48 kHz・サンプル単位で作る。プレビューは同じ DSP を AudioWorklet で動かす。リサンプルの変換器を固定し、カットの端に数 ms のマイクロフェード。速さを変えた音のピッチの扱いを決める。
6. 変形は 4x4 の行列で掛け合わせ、素材を 1 回だけ再標本化する（ラスタにも「トランスフォームを折りたたむ」）。縮めるときは面積の平均か Lanczos、広げるときは bicubic、どちらも線形の光で。モーションブラーの口（シャッター角、フレームの間の時刻）。マスクは被覆率のアンチエイリアス。合成モードの式は W3C Compositing and Blending Level 1。文字の画素への吸着で、ゆっくり動かすと跳ねる。大きさは画面上で描き、平行移動は合成の側でかける。
7. `FrameContext` にカメラの欄を空け、3D に広げる余地を残す。

### Chrome の GPU 基盤

1. DOM の文字を毎フレーム WebGL に入れる標準の手段はない。文字を時間で変わらない絵として、キーごとに 1 回だけラスタにする。ラスタの裏（HTML-in-Canvas、foreignObject）は差し替えられるようにする。書き出しの Chrome は版を固定できるので、origin trial のフラグを強制して使える。
2. 書き出しの出口（上と同じ）。本番の画質の細かい指定（2 パス、10 bit、CQ）が要るなら、GPU で NV12 に変換、PBO と fence で非同期に読み、バイナリの WebSocket で Node へ、FFmpeg の NVENC の stdin へ、の経路を併用する。
3. headless の GPU とハードウェアデコードの確認を最初の作業にする。
4. デコーダは素材ごとに 1 つを使い回すプール（同時 4〜6 本）。`VideoFrame` は描いた直後に必ず `close()`。OBS の色空間の確認。WebGL の文脈は 1 ページ 16 個までなので 1 つに集める。コンテキストロストからの復帰と、書き出しの区間単位の再開。
5. 音の書き出しの経路が設計書にない。

### プロの映像編集者

1. 画面をページで分けずにパネルにする。常にプログラムモニター、タイムライン、Inspector を出し、Story は左、Review は右、グラフエディターは下のタブ。Media と Deliver だけ別画面。再生位置と選択は全体で 1 つ。
2. 字幕や札を「カットに接続」できるようにし、リップルで一緒に動かす（Premiere のリンク、FCP の接続クリップ）。最重要の抜け。
3. 本編とショートの関係を「参照」と「複製して分岐」の 2 つで持つ。参照でもカットの in/out だけ上書きできる（上書きの印）。分岐は元との対応を残し、元が変わったら知らせる。どのカットがどのショートで使われているかを本編に印で出す。縦への再フレーミング（見せたい所）と字幕の置き場所は、コンポジションごとに別の値を持てる。
4. AI の変更を「対応 1 回」のまとまりにし、まとまりごとに承認・却下・取り消し。タイムラインに変わった所を色で出す。人が直した所を AI が上書きしないロック。変わった所だけを前後 2 秒ずつ続けて再生する。数値の点検（無音、つなぎ目）を変わった所に注釈で付ける。
5. Story に「使っている・使っていない」の色分け、採用・却下・保留を 1 キーで、話題の概観と使用率、検索の結果をそのまま selection に、収録の中の編集者への指示を別の印に。
6. オーディオミキサー（役割ごとのバス、LUFS のメーター、ダッキング）がない。
7. 喋りの継ぎ目の自動処理（短いクロスフェード、無音の詰め）、スナップ、マーカー（YouTube のチャプターの書き出しも）、字幕のトラックと SRT・VTT・YTT の書き出し、名前つきのスナップショットと差分、自動保存とクラッシュからの復元、VR の別撮りと画面収録の同期、トランジションの音、取り込みの段階表示（波形と文字起こしを先に）、プロジェクトをまたぐ素材とテンプレートのライブラリ。Avid の `M` `,` `.` `/` は日本語のキーボードで扱いにくいので、J/K/L、矢印、`[` `]` を先に。マルチカムとカラーの本格的な補正は要らない。

### 保守と品質

1. 自動の改善を別の worktree で動かし、検査とテストが通ったら本線へ取り込む。動いているサーバーは本線を読むので、壊れた回は本線に届かない（Dependabot、Renovate の PR の型）。
2. 回の中では、プロジェクトの置き場所を見本のプロジェクトに向け、実際のプロジェクトは権限の外に置く。回の前後で実際のプロジェクトのハッシュを比べ、違えば失敗にして戻す。回の前にスナップショットを取る。
3. 回の予算（ターン、時間、費用）、すぐ止める手段（プロセスグループごと kill）、連続して失敗したら自動で止める。回ごとに 1 コミットにし、戻すのは revert 1 回。レンダラー・操作の層・スキーマの移行は、人の承認が要る領域にして PR までにする。自動の起票は 1 時間あたりの上限を設け、回の直後の例外はその回の疑いとして紐づける。
4. テストの章を足す: 小さい固定の解像度で決まった時刻のフレームを描き、見本の絵と許容差つきで比べる（SwiftShader で固定）。プレビューと書き出しの一致を比べるテスト。操作の取り消しの性質テスト（fast-check。apply→undo で元に戻る、apply→undo→redo が apply と同じ、決定的、断った操作は文書を変えない）。キーフレームの補間の性質テスト。版ごとの見本の文書（`fixtures/v1.json` …）からの移行テスト（移行は 1 版ずつの純関数）。音は数値で比べる。
5. ノードの隔離: `render` の例外を受けて、そのレイヤーだけ透明とエラーの印にする。GL の文脈を種類に直接渡さず、描画先とヘルパーだけを渡す（GL の状態を汚させない）。`prepare` と `render` に時間切れ。壊れた種類は一時的に無効にする。重い種類（Three.js、生成 AI）は後で別の文脈や Worker に移せる口にしておく。種類ごとに `migrate(oldParams, fromVersion)`。`deterministic` の自己申告は、2 回描いて同じかを自動で確かめる。全種類に共通の契約テスト（既定値で描ける、端で例外なし、`vector` なら 2 倍で描けて縁が崩れない、キーが安定）。
6. 進め方を組み替える: 最初に「素材 1 本を切って文字を載せて書き出す」を最後まで通す。書き出しの速さ、プロキシのフレームの正確さ、音と映像のずれ、`text.html` の画素の差は、段階 2 の最初に数日の試作で測り、数字を設計書に戻す。自動の改善は基盤が安定した後にする。実際のデータでの確かめを前に出す（終わった回の再現で）。
7. ops.jsonl と文書のどちらが正かを決める。取り込みの付属ファイルにも版と JSON Schema。費用のかかる `gen.ai` を自動の改善の回が呼べないよう、操作の側で見積もりを強制する。
