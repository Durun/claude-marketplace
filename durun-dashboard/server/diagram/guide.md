# 図解技法カタログ

図解の資料を組むときの表現技法を定める。
技法ごとの書き方は、例ファイルとして `examples/` に置いてある。
使う技法の例ファイルを読み、マークアップと `<style>` を写して中身を差し替えるのが基本の作り方である。

## 資料の組み立て

書き手が書くのは `<body>` の中身だけである。
doctype と `<head>`、共通の CSS と JavaScript（`assets/` の base.css、base.js、preview.css、preview.js）は、ダッシュボードが足して 1 枚の HTML にする。
例ファイルの `<link>` と `<script src>` は写さない。

例ファイルが自前の `<style>` を持つときは、その `<style>` を本文の先頭に写す。
本文の `<style>` は共通の CSS より後に読まれるので、共通の指定を上書きできる。

外部のスクリプト、スタイルシート、画像、フォントは読み込まない。
資料は 1 枚の HTML で完結させる。

## 技法カタログ

内容の種類から技法を選ぶ。
迷ったら、読み手の認知負荷が軽い方を選ぶ。
図解の割合を多めにする。

| 内容 | 技法 | 例ファイル | 選ぶ基準 |
|---|---|---|---|
| 状態や区分の表示 | バッジ | `examples/badges.html` | 他の技法の中で使う語彙。意味色の対応をここで揃える |
| 受け入れ条件と検証ケース | 検証シナリオツリー | `examples/scenario-tree.html` | 前提条件が複数のケースで重複するとき。前提条件を親へくくり出し、兄弟の並び順で実行順を表す。操作と事後条件は削らない |
| フェーズと手順 | ステッパー | `examples/stepper.html` | 4 段以上で、現在地の強調が要るとき。3 段以下は番号リストにする |
| 挙動や構造の変更 | Before/After 対比 | `examples/before-after.html` | 差分が本体のとき。左右のレイアウトを揃える |
| コンポーネント間の呼び出し | 手書き SVG フロー図 | `examples/flow-svg.html` | 接続関係そのものが情報のとき。矢印に必ずラベルを付ける |
| 状態遷移 | バッジ列と遷移表 | `examples/state-transition.html` | 禁止遷移が論点なら遷移表にする。状態が 3 個以下ならバッジ列だけでよい |
| システム内の位置づけ | 入れ子ボックス構成図 | `examples/container-boxes.html` | 包含関係だけなら、線のない HTML の入れ子で足りる |
| コード断片 | コードブロック | `examples/code-block.html` | 字面そのものが内容のとき。抜粋に絞り、20 行を超えるなら details へ畳む。型なら data-structure、HTTP の実例なら http-api を選ぶ |
| データ構造 | テーブルカードと TypeScript の型 | `examples/data-structure.html` | リレーショナルなデータは多重度のラベル付きカードにし、入れ子のデータは型注釈で曖昧さを消す |
| HTTP 通信 | API リファレンスカード | `examples/http-api.html` | 単一の API の契約は、パラメータの表、ステータスの表、生の HTTP の実例で示す。呼び出し順が論点ならフロー図にする |
| 分岐と条件の論理構造 | 条件ツリー | `examples/condition-tree.html` | 分岐が本体のとき。合流やループが出たら SVG フロー図にし、網羅性が論点ならデシジョンテーブルにする |
| ファイル構成の変更 | ファイルツリー | `examples/file-tree.html` | ファイルの置き場所が判断の対象のとき。変更のないファイルは省くか details へ畳む |
| モックやスタブでの差し替え | 差し替えフロー図 | `examples/mock-swap.html` | フローの一部が実装ごと入れ替わることが論点のとき。差し替え点（インターフェース）を破線で示す |
| PR の積み上げと分割 | PR スタック | `examples/pr-stack.html` | base branch が未マージの PR のとき。上が最後にマージする段にする。各行は PR へのリンクにする |
| 並行して進む処理の時間配分 | 時間軸レーン図 | `examples/timeline-lanes.html` | 占有、待ち、重なりが論点のとき。レーンは同時に動く主体、横軸は時間にする |
| 位置や寸法によるしきい値の判定 | 幾何と判定境界の図 | `examples/geometry-threshold.html` | 空間的な関係が判定式そのもののとき。2 つの状態を同じ座標系で並べる |
| 実測値と予算の対比 | 予算線付きの横棒 | `examples/budget-bar.html` | 値が 2〜4 個で、しきい値の内外が結論のとき。内訳と削減の経緯まで示すなら表にする |
| 完成物の見た目と動き | プレビュー領域 | `examples/preview-pane.html` | 静止画では動きが伝わらないとき。1 つの実演で見せる動きは 1 つにする。動く実演にはリセットを付ける |
| 用語の説明 | 用語集と自動ホバー | `examples/glossary.html` | 読者が知らない語が 3 つ以上あるとき。文書末の一覧だけだと読み手が往復するので、ホバーと併用する |
| 見出しの目次 | 右端の目次 | `examples/outline.html` | 書き手は何もしない。見出しが 3 個以上あれば base.js が組み立てる |

PR 番号、Issue 番号、文書名は、会話に URL があれば実際に飛べるリンクにする。

## HTML/CSS と SVG の切り分け

要素のあいだに線が要らなければ、HTML と CSS で作る（カード、バッジ、表、入れ子ボックス、details）。
ノード間の接続関係そのものが情報のときだけ、手書きの SVG にする。
自己完結を保つため、Mermaid などの外部ランタイムは読み込まない。

SVG の作法は次のとおりである（詳しくは flow-svg.html のコメントにある）。

- `viewBox` で大きさを決め、CSS の `max-width: 100%` で縮める。
- 線と文字は `currentColor` にして、明るい画面と暗い画面の両方に追従させる。意味色は変更点の 1 色だけにする。
- `<figure>` と `<figcaption>` で包み、`role="img"` と `aria-label` に図の主張を書く。

## アイコン

アイコンが要るのは、色に頼らず種類を区別したいときと、線でつないだ節点を明示したいときである。
Git や PR の状態には Octicons（MIT License）を使う。
GitHub の画面と同じ絵になるため、読者が意味を推測しなくて済む。

pr-stack.html の非表示の `<svg>` に、よく使う 4 つの絵を `<symbol>` で定義してある。
id は `i-draft`（Draft の PR）、`i-open`（開いている PR）、`i-merged`（マージ済み）、`i-branch`（ブランチ）である。
使う絵の `<symbol>` だけを、本文の非表示の `<svg>` に写す。
呼び出し側は `<use href="#i-open">` で参照し、`fill: currentColor` でテーマと状態の色に追従させる。

## プレビュー領域

完成物の見た目や動きそのものを説明したいときは、文書の中に区切った領域を作って実物を動かす。
preview.css と preview.js はダッシュボードが入れるので、`<figure class="preview">` の中に `<template>` で実演の中身を書くだけでよい。
書き方は preview-pane.html をそのまま写せばよい。

実演は Shadow DOM に入るため、実演の CSS は文書の本体へ漏れない。
`--fg` などのカスタムプロパティは境界を越えるので、実演の中でもテーマの色をそのまま使える。
`data-reset` を付けると「初期状態に戻す」ボタンが出て、何度でも最初から試せる。
動きのある実演には必ず付ける。

`data-height="14rem"` は実演の面の高さを決める。
中身を `position: absolute` だけで組んだ実演は自分の高さを持たないため、指定しないと既定の高さまで縮んで中身が隠れる。
面からはみ出した要素は切り取られるので、実演の中身は面の内側に収める。

iframe を使わないのは、1 枚の HTML で完結させるためと、実演の中身を素の HTML として書けるようにするためである。
その代わり JavaScript は隔離されないため、実演のスクリプトは渡された `root` の配下だけを触る。

## 共通スタイルと色ルール

base.css と base.js は、どの資料にもダッシュボードが入れる。
色は base.css の変数（`--fg`、`--muted`、`--ok` など）で書く。
変数は、明るい画面と暗い画面の両方に追従する。

色は意味で固定する。
緑は採用と正常、赤は禁止と異常、青は変更点と新規、グレーはスコープ外と既存を表す。
新規と既存の変更を分けたいときだけ、黄（`--mod` と `.badge.mod`）を「既存物の変更」に足す。
ファイルツリーがその代表例である。
同じ意味は文書全体で同じ色にし、色だけに意味を担わせない（バッジのラベルやアイコンを併記する）。

リンクは `--new` の青にする（base.css で指定済み）。
h1 の直後に要約 1 文を置くときは、`<p class="subhead">` にする。

## 用語集

用語集を置くときは、文書末に用語集のテーブルを置き、それを囲む `<details>` へ `id="glossary"` を付ける。
base.js は `#glossary table` でテーブルを引くため、`id` をテーブル自身や見出しへ付けると用語のホバーが出ない。
書き方は glossary.html をそのまま写せばよい。

本文は編集しない。
base.js が読み込み時にテーブルを読み、本文中の初出（h2 の節ごとに 1 回）を点線の下線付きの `.term` へ置き換える。
用語を増やすときも、テーブルへ 1 行足すだけでよい。

用語集の `<details>` は閉じた状態で置く（`open` を付けない）。
本文のホバーで読めるため、一覧を最初から広げると文書末が長くなるだけである。

## 全体構成の原則

- **BLUF**：各セクションの冒頭に結論を 1 文で置く。図には「この図が言いたいこと」のキャプションを付ける。
- **1 画面 1 メッセージ**：1 つの図が答える問いは 1 つにする。分岐と時系列、構造と手順を混ぜたくなったら分割する。
- **Progressive disclosure**：エッジケースと補足は `<details>` へ畳む。
- **階層と抽象度の対応**：全体像、変更点、詳細の順に並べ、途中で読むのをやめても誤解しない構成にする。

## アンチパターン

- 散文の再掲としての図。図は、散文で表せない関係を持つときだけ作る。
- 全部盛りの図（構造とフローと例外を 1 枚に詰める）。読者が入口を見つけられない。
- 5 色以上の意味色、意味のない色分け、セクションごとに変わる配色。
- 装飾の過多（影、グラデーション、絵文字での状態表現）。
- 凡例のない独自の記法（破線、色、矢印の向きに意味を持たせたのに、説明がない）。
