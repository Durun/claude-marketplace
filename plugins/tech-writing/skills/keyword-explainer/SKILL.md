# Keyword Explainer

キーワードを受け取り、1次情報にあたって調査し、Notionに解説ページを作成する。
読者は「そのキーワードを初めてキャッチアップするエンジニア」。あとで読み返したときに、根拠となる1次情報へすぐ飛べることを重視する。

## Step 1: 調査

まずキーワードが何か（OSSライブラリ / SaaS / プロトコル・概念 / 社内ツール等）を見極め、それに応じて情報源を選ぶ。

1. **公式リファレンス**: WebSearch で公式ドキュメントサイトを特定し、WebFetch で主要ページ（概要、アーキテクチャ、主要機能、料金・制約など）を読む。ブログ記事やQiita等の2次情報は、公式情報の補助としてのみ使う。
2. **リポジトリのドキュメント**: GitHub リポジトリがあれば README、`docs/` ディレクトリ、examples を読む。`gh api` や raw.githubusercontent.com 経由で取得すると速い。

調査中は「ページに書くポイント」と「その根拠となるURL」をペアでメモしておく。あとからリンクを探し直すと漏れるため、読んだ時点で対応づけるのが確実。

### GitHub permalink の作り方

ファイルにリンクするときはブランチ名のURLではなく、コミットSHA付きの permalink を使う（ブランチURLは将来の変更で行番号がずれ、リンクの意味が壊れるため）。

1. デフォルトブランチの最新コミットSHAを取得する:
   `gh api repos/{owner}/{repo}/commits/{branch} --jq .sha`
   （gh が使えない場合は `git ls-remote https://github.com/{owner}/{repo}.git HEAD`）
2. `https://github.com/{owner}/{repo}/blob/{sha}/{path}#L{開始行}-L{終了行}` の形式で組み立てる。
3. リンク先の行番号が正しいか、対象ファイルのその行を実際に確認してから書く。

## Step 2: 既存ページの確認

ページを作る前に、同じキーワードのページが解説ページ用の Notion データベースに既にあるかを確認する。DB を「1キーワード1ページ」に保ち、同じ事実が複数ページに散らないようにするため。

1. `mcp__notion__notion-search` でキーワードを検索する。正式名称・略称・表記ゆれ（`OpenTelemetry` / `OTel`、`ClickHouse` / `clickhouse` など）をそれぞれ試す。`data_source_url` に対象 DB の URL を指定すると DB 内に絞れる。
2. 候補が見つかったら `mcp__notion__notion-fetch` で本文を読み、既にどこまで書かれているかを把握する。

読んだ内容と今回の調査結果を突き合わせ、次のように扱う。

- **同じキーワード・同じ文脈**: 新規作成せず、既存ページを `mcp__notion__notion-update-page` で更新する。古い記述や陳腐化した仕様は差し替える。`Last Reviewed` を当日に更新し、`Status` と `Tags` も現状に合わせて見直す。
- **同じキーワードだが文脈や観点が違う**（別プロダクトでの使い方、メジャーバージョン違い、扱うレイヤが違う等）: まず既存ページに節を足して補足する。補足が長くて親ページの見通しを損なう場合、または単独で読みたいまとまりになる場合は、既存ページの子ページとして分割し、親ページの該当箇所から子ページへリンクする。
- **名前が似ているだけの別物**（同名の別プロダクト等）: 別ページとして新規作成し、タイトルに区別の付く補足を入れる（例: `Vault (HashiCorp)` / `Vault (WorkOS)`）。互いに本文冒頭で「これは〜ではない」とリンク付きで示し、必要なら `Related` で結ぶ。

どの場合も、同じ事実を2箇所に書き写さない。片方に書き、もう片方からはリンクで参照する。

## Step 3: Notion ページの作成

`mcp__notion__notion-create-pages` を使い、解説ページ用の Notion データベースの子ページとして作成する（既存ページの更新・補足に落ち着いた場合は、この節のガイドラインを更新内容にそのまま適用する）。

対象の DB は環境変数 `TECH_WRITING_NOTION_DB` で指定する。
`TECH_WRITING_NOTION_DB` は解説ページを作る Notion データベースを指す環境変数で、値は DB の URL である。
未設定であれば、どの DB に作るかをユーザーに尋ねる。推測で決めない。

`parent` には DB の data source ID を `{"type": "data_source_id", "data_source_id": "..."}` の形で指定する。
data source ID は `mcp__notion__notion-fetch` で DB を取得して調べる。

ページタイトルはキーワード名（必要なら短い補足を付ける。例: `hono (web framework)`）。本文は日本語で書く。

### DB プロパティの設定

新規ページを作成するときは、対象 DB が持つプロパティを埋める（`properties` に指定する）。
DB のプロパティ構成は環境ごとに違うため、`mcp__notion__notion-fetch` で DB を取得して実際の定義を確かめてから埋める。

次のプロパティがあれば、この方針で埋める。

- **Title** *(必須, title)*: ページタイトルと同じ値。
- **Status** *(select)*: 通常は完成を表す値（`Explained` など）。作業中に途中保存する場合は `In Progress`、着手前は `TODO`。実際の選択肢は DB の定義に合わせる。
- **Tags** *(multi_select)*: 関連するタグを JSON 配列で。例: `"[\"backend\", \"web-framework\"]"`。まず DB の既存タグから選び、適切なタグが無い場合は新規タグ名を追加してよい（multi_select は新規値を許容する）。
- **Source** *(text)*: 発見元やコンテキスト。例: `/keyword-explainer (<リポジトリ名>)` や `Slack #dev-random 2026-07-05`。
- **Last Reviewed** *(date)*: 作成日を `date:Last Reviewed:start` に ISO-8601 の日付で入れる（`date:Last Reviewed:is_datetime` は `0`）。

`Created` のような `created_time` 型は自動設定されるので指定しない。`Related` は他のDB内ページとの関連付けが明確なときだけ設定する（通常は空でよい）。

### ページ構成

キーワードの性質に合わせて柔軟に構成してよいが、基本形は以下:

```
# 概要（それは何か、何を解決するか）
# 主要な概念・機能
# 仕組み / アーキテクチャ
# 使い方・コード例
# 注意点・落とし穴
# 参考リンク（調査で使った1次情報の一覧）
```

### 執筆ガイドライン

- **ポイントには1次情報リンクを添える**: 事実や主張を書いたら、その根拠となる公式ドキュメントやリポジトリへのリンクを「そのポイントのそば」に置く。ページ末尾の参考リンク一覧だけに寄せない。読者が「これ本当？」と思った瞬間に確認できるようにするため。
- **ファイルへのリンクは GitHub permalink**: ソースコードに言及するときは、上記の手順で作った permalink を使う。
- **コードを引用するときは permalink + コードブロック**: Notion の code preview ブロックは API 経由で作成できないため、permalink を添えたコードブロックで代用する。
- **mermaid で図示する**: アーキテクチャ、データフロー、コンポーネント間の関係など、文章だけでは追いにくい構造は ```mermaid コードブロックで図示する（Notion はmermaidをレンダリングできる）。すべてに図が必要なわけではなく、「文章で3文以上かかる関係性」が目安。

## Step 4: 報告

作成が完了したら、ページのURLと、調査した情報源の要約をユーザーに報告する。新規作成か既存ページの更新・補足かも明記し、既存ページを触った場合は何を差し替えたか・何を足したかを添える。
